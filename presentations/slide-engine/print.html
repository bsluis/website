slide-engine 101

A Markdown-powered, web-standards-first presentation engine. Built with Lit, CSS custom properties, and a healthy disregard for unnecessary complexity.

Notes: Welcome. This is the first presentation ever built with slide-engine — which means it is also the system's first real test. No pressure.

Slide 2 · title

The problem with other systems

  • Framework bloat — you wanted slides, you got a build pipeline the size of a small country
  • CDN dependencies — your fonts vanish the moment the conference Wi-Fi dies
  • Monolithic pages — one giant DOM for 60 slides, fighting the browser all the way
  • Magic everywhere — great until it isn't, and then you're reading source code at midnight

Notes: Set the scene. Most presentation tools are either too heavy, too opinionated, or they phone home to a CDN at the worst possible moment — right before you go on stage.

Slide 3 · three-col

Built on three pillars

Pipeline

A Node build script reads src/slides.md and emits one HTML file per slide into dist/. No bundler magic — just fs.writeFile and a fast loop.

Design System

Lit web components, atomic design, and a full CSS custom property token system. Every visual value is a token. No hardcoded anything.

Runtime

A tiny client-side module handles keyboard navigation, fullscreen, view transitions, and a service worker that precaches everything for offline use.

Notes: Walk through each pillar briefly. Pipeline is Phase 1, Design System is Phase 2, Runtime is Phase 3.

Slide 4 · content-image

A homegrown CMS

Each slide is a fenced block in a single Markdown file. Slot fences map content to web component slots — no GUI, no database.

---
type: content-image
title: My Slide
notes: Speaker notes go here.
---

::: left
- Point one
- Point two
:::

::: right
![Diagram](diagram.png)
:::

Why this works

  • One file, one source of truth
  • Plain text — version-controlled, diffable, grepable
  • Slots are explicit — no guessing where content lands
  • The pipeline validates every slide at build time and fails loudly on errors
  • Works in any editor, on any machine, forever

Notes: This is the part that makes slide-engine genuinely different. The Markdown format with slot fences lets you write structured content without a GUI, without a database, and without losing your mind.

Slide 5 · content-image

Multi-page — on purpose

One HTML file per slide.

Navigation is a real browser navigation. View transitions make it feel instant.

export function navigate(url) {
  if (document.startViewTransition) {
    document.startViewTransition(() => {
      window.location.href = url
    })
  } else {
    window.location.href = url
  }
}

Why multi-page wins

  • Each slide is a standalone document — inspect it, share it, link directly to it
  • The browser's back/forward cache handles history for free
  • No virtual DOM, no reconciliation, no surprises
  • Progressive enhancement: degrades gracefully when the Transitions API is absent
  • The service worker precaches every slide before you go on stage

Notes: This is the big architectural bet. Most presentation tools render all slides in one page and animate between DOM states. slide-engine goes full multi-page and uses the View Transitions API instead.

Slide 6 · three-col

Why it's different

Plain vanilla

No runtime framework outside Lit for components. CSS does the heavy lifting. JS only where CSS cannot do the job. The codebase you can read in an afternoon.

Truly offline

Self-hosted fonts. Precached assets. A service worker that activates before your talk starts. The Wi-Fi can die and nobody in the audience will know.

Built by Claude

Every line of code in this system — the parser, the components, the runtime, even this presentation — was written pair-programming with Claude. AI-assisted, human-directed.

Notes: The three things that make slide-engine worth building. These aren't just technical choices — they're a philosophy.
